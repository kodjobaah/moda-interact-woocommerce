# ARCH-046-WOOCOMMERCE-002 — Woo pre-submit consent capture

This is the Woo-owned **producer** for the pre-production **v2-only** hosted API contract (`ARCH-046-API-007`). It does not grant consent by displaying the optional checkbox, collecting a billing phone, storing order meta, or publishing checkout activity. The hosted API is the sole durable current-consent/evidence writer. Real Classic/Blocks/HPOS checkout verification is owned by `ARCH-046-SYSTEM-TEST-001`.

## Before order placement

- **Classic:** Woo's `woocommerce_checkout_update_order_review` executes after its own checkout nonce guard. The plugin additionally verifies the `update-order-review` nonce in the PHP callback. A small packaged browser script triggers Woo's supported `update_checkout` lifecycle when Moda's registered checkbox changes. PHP observes the current Woo checkout session/cart and billing phone/country from the validated checkout form. An initially unchecked checkbox is neutral; an explicit check after valid billing details records GRANT. An explicit same-checkout uncheck of a previously checked state records REVOKE. Ordinary refreshes never revoke permission.
- **Checkout Blocks:** The consent control remains in the main Checkout Fields column, with its existing runtime mount for previously saved checkout templates. All deliberate Blocks consent actions and proof-backed status checks now use WooCommerce's supported `extensionCartUpdate` → `/wc/store/v1/cart/extensions` path. WooCommerce supplies the authenticated Store API session and handles the Nonce/Cart-Token; Moda does not initialise sessions, carts or customer objects in separate WordPress REST calls. The server callback compares the browser's expected billing phone to the **server-observed** Woo customer phone (a mismatch is rejected, never stored as a grant) and invokes the existing consent capture or API-006 reader. The response exposes only a request ID, bounded outcome, boolean confirmation and a fixed reason code in `cart.extensions['moda-interact-consent']`. The grant event, phone and shopper proof are never sent back to JavaScript. An opt-in before a billing phone is entered remains pending only in the UI and is retried when the cart store observes a contact. Normal cart/checkout updates alone cannot grant or revoke consent.

- Both modes recheck a live cart, exact checkout key, Woo session identity and current WordPress login ID. No session or cross-login/phone-change may inherit a previously selected box; a changed phone must be unchecked and explicitly reselected. The field is optional and starts unchecked. A first unchecked observation creates **no** REVOKE and **no** GRANT. Positive actions also recheck connected installation and effective recovery entitlement.

The Classic presentation checkbox uses `moda_interact_whatsapp_recovery_opt_in`; the Blocks presentation is a dedicated Checkout Fields control with a Woo Store API extension callback. The authenticated PHP producer verifies the checkout nonce, Woo session and billing contact locally; those WordPress-specific attestations are not sent to Moda. New checkbox grants use `moda.woo.whatsapp-recovery-marketing.v3` with the short, translated opt-in label `Send me WhatsApp shopping updates, reminders and offers.` The label does not repeat the merchant name or URL, which are already identified by the checkout. The locale is the configured WordPress Site Language (`WPLANG`), not the current administrator's personal language. Classic and Blocks display the same translated label that the API records as immutable disclosure evidence. The API derives the merchant identity from installation authentication; the displayed disclosure does not include the merchant URL. Consent purpose and delivery authorisation remain **WHATSAPP_CHECKOUT_RECOVERY only**; the displayed wording does not authorise general campaigns.

## Hosted acknowledgement and retries

The plugin sends `POST /v1/woocommerce/whatsapp-consent` with the existing installation bearer headers and the **exact** six-field v2-only event shape. On `200 recorded/duplicate` it retains the immutable grant event ID as a server-only returning-customer proof pointer; neither this plugin nor checkout activity changes current consent except via the acknowledged hosted API write. A timeout/503 does not block placing an order, does **not** produce an ACK or imply recoverability, and schedules a small number of retries through Action Scheduler using the **identical** event ID/body. Revoked/replaced installations, invalid canonical site identity and stale actions fail closed. The hosted API serializes and rejects a late GRANT behind a newer REVOKE/STOP. Grant actions older than four minutes are not retried; this is request freshness, not permission expiry.

If an ordinary checkout activity event arrives before API ACK, that checkout can remain ineligible. There is **no** consent-triggered recovery wake-up or checkout rescan. The checkout publisher optionally uses authenticated `woo.activity.v2` HTTP for verified canonical phone contact, projected by the API into the existing `woo.activity.v1` background queue schema; v1 events remain supported and neither activity version produces consent. The current generated provider event and contact never contain customer consent booleans.

## Identity and portability

The test-only `tests/fixtures/identity-v1.shared-2.5.0.json` is a byte-identical snapshot of the published `@modainteract/moda-interact-shared@2.5.0/identity/fixtures` JSON, pinned to SHA-256 `0f5b16e3fac34e80c1fed814095bc8d2be9a46e69e5047378f8ef9d844f66e15`. The PHP compatibility test executes every applicable `phoneCases` and recipient-lifecycle vector. Shopify Customer IDs/GIDs are explicitly excluded. This is a fixture, not a PHP runtime copy of the Shared library.

PHP's bounded normalizer covers the fixture's verified GB/US/FR national numbers and explicit E.164-format input. For national numbering plans without verified server country support it fails closed rather than guessing; the hosted API revalidates **every** canonical recipient using the complete published Shared identity implementation and refuses unsupported/mismatched/ambiguous numbers. Extending PHP validation to all international national-number formats would require an approved PHP numbering library; this bounded producer does not claim comprehensive international phone validation from PHP alone.

## Validation ownership

Unit/contract validation in the Woo plugin checks nonce/session/cart-token assertions, transitions, changed phones, replays, API failures, installation rotation, canonical identity fixtures, field presentation, packaging and build/lint. The separate terminal system-test task validates real browser/WordPress Classic and Blocks flows, HPOS, authenticated guest nonce/cart tokens, before/after ACK ordering, abandon-before-order, disabled recovery, account switching and 20-locale rendering. The Woo implementation should not claim those system tests passed from PHP stubs alone.

## Merchant-site impact of Store API integration

The Blocks extension callback only reads existing WooCommerce session/cart/customer objects. It never calls `wc_load_cart()`, changes billing addresses, line items, totals, coupons, stock or order state, or uses Moda-hosted credentials in the browser. However, **the WooCommerce Store API `cart/extensions` request itself is a native cart-update cycle** and may run Woo's own calculation/third-party hooks. It is invoked on initial checkout status lookup, contact changes and deliberate consent actions—not on each keypress or unrelated cart refresh. The client sets `overwriteDirtyCustomerData: false` so Woo is not instructed to overwrite unsaved checkout inputs. If the server-observed phone differs from the current displayed phone, the action fails closed with an accessible retry message. Do not claim the native Store API cycle is side-effect-free without a LocalWP test with representative shipping/payment extensions.

Classic checkout continues to use Woo's `update_order_review` hooks and its existing scoped WordPress REST status/withdrawal actions. The obsolete Blocks-specific custom `/checkout-consent/choice` route is no longer registered; Blocks does not call the custom WordPress REST endpoints, the hosted API or a developer's `localhost` directly. All server-to-server consent and proof API requests still use the authenticated Woo installation. Automatic opt-in and silent uncheck-to-revoke remain prohibited; consent needs a verified, deliberate action and a hosted acknowledgement.
