# ARCH-046-WOOCOMMERCE-002 — Woo pre-submit consent capture

This is the Woo-owned **producer** for the accepted hosted API contract `woo.whatsapp-consent.v1` (`ARCH-046-API-001`). It does not grant consent by displaying the optional checkbox, collecting a billing phone, storing order meta, or publishing checkout activity. The hosted API is the sole durable current-consent/evidence writer. Real Classic/Blocks/HPOS checkout verification is owned by `ARCH-046-SYSTEM-TEST-001`.

## Before order placement

- **Classic:** Woo's `woocommerce_checkout_update_order_review` executes after its own checkout nonce guard. The plugin additionally verifies the `update-order-review` nonce in the PHP callback. A small packaged browser script triggers Woo's supported `update_checkout` lifecycle when Moda's registered checkbox changes. PHP observes the current Woo checkout session/cart and billing phone/country from the validated checkout form, and records only an unchecked→checked or checked→unchecked transition.
- **Checkout Blocks:** Woo's official Additional Checkout Field in the **order** location publishes changes to `PUT /wc/store/v1/checkout`. The `woocommerce_store_api_checkout_update_draft` callback runs after the Store API has updated and validated a fresh draft session. When Woo is updating an existing draft order, the separate `woocommerce_store_api_checkout_update_order_from_request` callback observes PUT/PATCH (never final POST). If a checkbox PUT precedes a billing phone, the explicit choice is staged briefly in the same verified WC session and published only once a later authenticated `cart/update-customer` request supplies a valid server-observed phone. Moda additionally requires a valid `wc_store_api` nonce or a Woo-validated Cart-Token bound to the **current** WC session before observing the posted field and current WC customer billing phone. Place-order POST metadata is not a grant.
- Both modes recheck a live cart, exact checkout key, Woo session identity and current WordPress login ID. No session or cross-login/phone-change may inherit a previously selected box; a changed phone must be unchecked and explicitly reselected. The field is optional and starts unchecked. A first unchecked observation creates **no** REVOKE and **no** GRANT. Positive actions also recheck connected installation and effective recovery entitlement.

The presentation checkbox uses Classic `moda_interact_whatsapp_recovery_opt_in` or Blocks `moda-interact/whatsapp-recovery-opt-in`. The authenticated PHP producer maps either to the canonical API `checkoutAction.fieldId = moda/whatsapp-checkout-recovery`; the browser never supplies the API attestation booleans. The visible disclosure and sent evidence are `moda.woo.whatsapp-recovery-marketing.v1` with BCP-47 locale, translated purpose wording and the authenticated installation's exact canonical site URL.

## Hosted acknowledgement and retries

The plugin sends `POST /v1/woocommerce/whatsapp-consent` with the existing installation bearer headers and the **exact** strict v1 event shape. On `200 recorded/duplicate` it retains the remote revision/sequence only as a validated ACK; neither this plugin nor checkout activity modifies the hosted current consent itself. A timeout/503 does not block placing an order, does **not** produce an ACK or imply recoverability, and schedules a small number of retries through Action Scheduler using the **identical** event ID/body. Revoked/replaced installations, invalid canonical site identity and stale actions fail closed. The hosted API serializes and rejects a late GRANT behind a newer REVOKE/STOP. Grant actions older than four minutes are not retried; this is request freshness, not permission expiry.

If an ordinary checkout activity event arrives before API ACK, that checkout can remain ineligible. There is **no** consent-triggered recovery wake-up or checkout rescan. The checkout publisher optionally uses authenticated `woo.activity.v2` HTTP for verified canonical phone contact, projected by the API into the existing `woo.activity.v1` background queue schema; v1 events remain supported and neither activity version produces consent. The current generated provider event and contact never contain customer consent booleans.

## Identity and portability

The test-only `tests/fixtures/identity-v1.shared-2.5.0.json` is a byte-identical snapshot of the published `@modainteract/moda-interact-shared@2.5.0/identity/fixtures` JSON, pinned to SHA-256 `0f5b16e3fac34e80c1fed814095bc8d2be9a46e69e5047378f8ef9d844f66e15`. The PHP compatibility test executes every applicable `phoneCases` and recipient-lifecycle vector. Shopify Customer IDs/GIDs are explicitly excluded. This is a fixture, not a PHP runtime copy of the Shared library.

PHP's bounded normalizer covers the fixture's verified GB/US/FR national numbers and explicit E.164-format input. For national numbering plans without verified server country support it fails closed rather than guessing; the hosted API revalidates **every** canonical recipient using the complete published Shared identity implementation and refuses unsupported/mismatched/ambiguous numbers. Extending PHP validation to all international national-number formats would require an approved PHP numbering library; this bounded producer does not claim comprehensive international phone validation from PHP alone.

## Validation ownership

Unit/contract validation in the Woo plugin checks nonce/session/cart-token assertions, transitions, changed phones, replays, API failures, installation rotation, canonical identity fixtures, field presentation, packaging and build/lint. The separate terminal system-test task validates real browser/WordPress Classic and Blocks flows, HPOS, authenticated guest nonce/cart tokens, before/after ACK ordering, abandon-before-order, disabled recovery, account switching and 20-locale rendering. The Woo implementation should not claim those system tests passed from PHP stubs alone.
